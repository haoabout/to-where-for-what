# to-where-for-what

**English** · [简体中文](README.zh-CN.md)

A trip-planning skill for AI coding assistants. It produces **a single
`trip.html`** — shortlist, map and guide in one file, openable by
double-click and shareable with the people you're traveling with.

Filtering and scheduling happen entirely in the page; the AI stays out of it:

```
A search places →(AI)→ ┌ ① shortlist ⇄ ② map (filter + schedule) ┐ →(AI)→ ③ guide
                       └     you iterate, everything live        ┘
```

## Install

```bash
npx skills add haoabout/to-where-for-what
```

Works with Claude Code, Codex, Cursor, OpenCode and 70+ other tools (via the
[Vercel skills CLI](https://github.com/vercel-labs/skills)). Once installed,
just say "help me plan a trip to Osaka" and it triggers.

Manual install: copy `skills/to-where-for-what/` into `~/.claude/skills/` (or
your tool's equivalent skills directory).

**Requirements**: Python 3.9+, standard library only — no pip install. The map
and weather need a network connection.

## What it does

**A · Exhaustive search**　35–50 candidates by category quota, with opening
hours, closure days, booking requirements, tickets and renovation status **all
verified online in the first pass** — otherwise you filter for an hour only to
find the place shut that day. Every place must carry a real source URL.

**B+C · You filter and schedule**　The map view puts three columns side by
side: shortlist ｜ schedule ｜ map.

- Rate each place **yes / maybe / no**; markers recolor instantly
- Drag a place into a day, or click its dot; reorder within a day by dragging
  or with ↑↓
- The map connects each day's places in order with a dashed line in that day's
  color — **detours are visible at a glance**
- A place can appear on several days, or twice in one day
- Changes auto-save back to `places.json` after a few seconds; no need to
  remember a save button

**D · Guide generation**　The AI writes **to the schedule you arranged**, never
regrouping it. Day-by-day timeline, transport tables, light and photography
windows, caveats. The cost summary and the all-places table are generated by
the page from the data, so they always match your choices.

The guide is laid out on **A4 sheets** — one section per sheet, the same type
size on every one, page numbers in the footer, and a rail down the left side to
jump between them. "Export PDF" goes through the browser's print dialog. A
`---` in `route.md` is where a new sheet starts.

## What's in the page

- **Map**: OSM vector basemaps (two independent sources backing each other up)
  plus **metro lines and stations pulled from OSM, in the official line colors**.
  Both vector basemaps come as a light/dark pair, switched from the map's own
  corner button — the page around it is a fixed light canvas with a dot
  matrix and paper surfaces on top, and has no theme switch of its own
- **Weather**: fetched live from Open-Meteo in the browser. A real forecast
  within 16 days; beyond that it falls back to 8-year historical averages,
  clearly labeled
- **Export**: CSV (imports straight into Google My Maps), KML, and the guide
  as a PDF via the browser's print dialog
- **Fallback chain**: vector → raster → Leaflet without WebGL → a static
  scatter plot when everything is down

## Interface language

The trip page's UI language follows `trip.output_language`: Chinese gets the
built-in Chinese interface, everything else the built-in English one. For any
other language, the AI translates the template's string table into the `ui`
field of `places.json` when creating the trip (contract in
`references/data-schema.md`). Weekday and date names localize automatically
via `Intl`.

## Long-term preferences

Stored at `~/.to-where-for-what/preferences.md` and reused across trips:
transport habits, stamina, interest weights, dietary restrictions, budget
tier, guide verbosity.

**Deliberately kept outside the skill directory** — updating or reinstalling
the skill (git pull, downloading a zip, deleting and reinstalling) never
touches it. The skill directory ships only the template.

## Updating

Your personal state is never touched by an update, whichever path you take:
`~/.to-where-for-what/preferences.md` and everything under your trips
directory live outside the skill and survive reinstalls.

The installed version is the `version:` field in
`skills/to-where-for-what/SKILL.md` frontmatter; `CHANGELOG.md` next to it
says what changed between versions — read it before updating, it flags
behavior changes you'd otherwise meet by surprise.

**If you've modified skill files yourself** (SKILL.md rules, `build.py`, the
template — legitimate power-user territory), install via git and commit your
changes locally; `git pull --rebase` then gives you a real three-way merge
with conflict markers. That is the only reliable way your modifications
survive updates — a zip overwrite loses them silently. Lightweight personal
rules are better off in `preferences.md`, which no update can touch.

**When you ask the AI whether to update**, it follows the decision ladder in
SKILL.md ("Updating this skill"): with git metadata it checks `git status`;
without, it compares your files against the release your `version:` points
at — unmodified installs update by plain overwrite, modified ones get a
per-file three-way merge, always merging the skill directory as one unit
(`build.py` and the template are coupled). After any update it re-runs
`validate.py` over existing trips to catch contract drift.

## Output

```
<trips_root>/2026-09-osaka/
├── brief.md          # trip parameters
├── places.json       # ★ the single source of truth
├── transit.geojson   # metro lines and stations
├── route.md          # guide body
└── trip.html         # build artifact
```

`places.json` is the single truth and the page is merely its rendering, so the
shortlist and the map can never disagree. Where trips are stored is your
choice; it's asked once on first use and recorded in the preferences file.

## Known limitations

- **Metro colors depend on OSM's `colour` tag**. Minor cities may lack it, in
  which case a fallback palette is used (avoiding colors already taken)
- **Transit durations and fares are as of the query date**. Trips are often
  weeks away and timetables and fares change — re-check before departure
- **Opening via `file://` has no auto-save**; you have to press the save
  button (browsers won't let a page write files without a user gesture).
  `--serve` is recommended
- The guide body is written by the AI after verifying online, **but you should
  still spot-check a few source links** before you go

## Development

```bash
python3 dev/test_validate.py                          # validator regression (43 cases)
python3 skills/to-where-for-what/scripts/build.py <trip-dir> --serve
```

`dev/` holds development-time material (regression tests, capability probes)
and isn't part of the install.

For local development a symlink is convenient — edits take effect immediately:

```bash
ln -s "$PWD/skills/to-where-for-what" ~/.claude/skills/to-where-for-what
```
