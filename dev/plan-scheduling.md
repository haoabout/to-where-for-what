# 排程阶段（分天与排序）实施计划

## 背景

现在的流程是 **A 穷举 → B/C 筛选与地图 → D 攻略**。D 阶段由 AI 一手包办「哪天去哪、什么顺序」，
用户只能事后接受或推翻。大阪的实测数据说明这一步必须交回给用户：

```
待排池 28 个（想去 8 + 待定 20），分布在 19 个片区
总时长 33.8 小时，两天可用约 20 小时  →  必须砍掉约 14 小时
其中「此花区 · USJ 万圣节惊魂夜」单点 8 小时，本身就是一整天
```

砍掉 14 小时是取舍，不是计算。取舍该由用户做。

因此在 C 与 D 之间插入 **排程阶段**：用户把地点分到各天、排出顺序，D 阶段的攻略据此展开。

## 范围

**本次做**：数据结构、校验、marker 编码、三栏布局与天容器、点选与拖拽、顺序线、卡片瘦身、
问卷补时间、暂存与回写。

**本次不做**：D 阶段攻略跟随分天结果（`route.md` 写法、攻略视图按天组织）。
等这一版验收通过后单独做，避免一次推平太多。

## 已敲定的决策

| 议题 | 结论 | 理由 |
|---|---|---|
| 一个点能否属于多天 | **能**，同一天里也能出现两次 | 世博会连着两天去、夜景白天各去一次、酒店每天都有 |
| 右侧池子的行为 | **不移除**，已排入的标灰 + 打天数角标 | 移除后无法再排进第二天；且副本关系比"搬移"更符合多天语义 |
| 实时可行性条 | **不做** | 时间够不够是判断题，交给用户和 AI 讨论 |
| 闭馆日 × 分配天 | **做，定 P0** | 这不是判断题，是那天去不了。不拦住 AI 会写出注定失败的路线 |
| 布局 | 左 = 景点清单｜中 = 日程栏｜右 = 地图，两侧栏都尽量窄 | 清单与日程相邻，拖拽不跨地图；地图拿到最大空间 |
| 日程栏形态 | 天数 ≤5 平铺，≥6 切日期胶囊只展开单天 | 长线行程平铺会退化成无限滚动 |
| 排程是否常驻 | **开关**，筛选=两栏 / 排程=三栏 | 三栏会把地图挤到 800px 以下，筛选阶段用不到天容器 |
| marker 编码 | **填充 = 天，描边 = 选择，数字 = 当天序号** | 见下方"视觉编码" |
| 地图图标能否拖拽 | **不能**，改点选 | 在 marker 上拖动与地图平移冲突，触屏尤其难用 |
| 卡片能否拖拽 | **能** | DOM 到 DOM，与地图零冲突 |
| 拖拽怎么实现 | **内联 SortableJS**（不走 CDN），另加上下移按钮保底 | 见"拖拽方案" |
| 右侧排序 | 选择优先、推荐度次之；保留"按区域"可切换 | "想去"是用户自己的决定，权重高于 AI 给的 tier |
| 酒店 | 数组里的普通条目，房子图标，**不参与序号编号** | 同日换店（A 退房、B 入住）要能表达 |
| 天数 | 由 `trip.days` 自动生成 + 允许加「第 0 天」 | 抵达当晚、末日半天都是常见形态 |

## 数据结构

`places.json` 新增顶层 `days`：

```jsonc
{
  "trip": { /* 不变 */ },
  "places": [ /* 不变 */ ],
  "days": [
    {
      "n": 1,                          // 0 表示"第 0 天（抵达当晚）"
      "date": "2026-09-12",            // 可为 null（第 0 天可能没有独立日期）
      "label": "第 1 天",
      "places": [
        { "id": "os-hotel-a" },                    // 酒店，不编号
        { "id": "os-014" },                        // → 显示序号 1
        { "id": "os-031", "note": "看夜场" },       // → 显示序号 2
        { "id": "os-hotel-b" }                     // 同日换店
      ]
    }
  ]
}
```

**顺序只存在数组里。** 不给 place 加 `day` / `seq` 字段——两处存同一件事必然打架
（删一个点要重排所有 seq）。页面渲染时现算。

不出现在任何 `days[].places` 里的 = 未分配。

`places` 条目用对象而非裸 id，是为了挂 `note`（同一地点两次访问的备注不同），
以后还能挂到达时间、时长覆盖。

### schema 补充

景点新增可选字段：

```jsonc
"kind": "attraction" | "lodging"      // 缺省 attraction
```

`lodging` 的地点：房子图标、中性色、不参与当天序号编号、不计入"景点数"统计。

## 视觉编码

### 规则

| 状态 | 填充 | 描边 | 数字 | 直径 |
|---|---|---|---|---|
| 未排入 | 纸色（近白） | 选择色 3px | 无 | 22px |
| 已排入 | **天色** | 选择色 3px，与填充间夹 1.5px 白色隔离环 | 当天序号 | 26px |
| 多天 | 天色**双色扇形**（conic-gradient） | 同上 | 首个天的序号 | 26px |
| 酒店 | 中性深灰 | 同上 | 无（房子图标） | 24px 圆角方 |

**空心 = 还没安排，实心 = 已经安排。** 这个心理模型不用教。

白色隔离环是必须的：没有它，深蓝填充配绿描边在复杂底图上会糊成一片。
描边必须 3px，2px 时绿/琥珀/灰在 22px 圆点上分辨不出来。

多天用 conic-gradient 是因为我们的 marker 是 **DOM 元素**而非 canvas 符号——
这是 DOM marker 相对矢量符号的实际优势。三天以上会碎，但那种情况极少。

### 天的配色

必须避开绿（想去）、琥珀（待定）、灰（不想去），否则填充与描边同色系。
且要足够深，白色序号数字压得住。

```
第 0 天  #546E7A  蓝灰
第 1 天  #2E6FD9  蓝
第 2 天  #7B3FB5  紫
第 3 天  #0F8A8A  青
第 4 天  #C2185B  洋红
第 5 天  #5D4037  棕
```

与地铁线路色可能撞车，但地铁层默认关闭、且线是细线而 marker 是实心圆带白环，
形态不同，实测时确认即可。

### 顺序线

同一天的点按顺序连线，用当天的颜色。绕不绕路一眼可见——这是"用户自己或和 AI
讨论后形成合理顺序"的抓手。

多天同时显示时，**非当前天降到 30% 透明度**，否则会成一团面条。

## 布局与交互

```
┌────────────┬────────────┬─────────────────────────────┐
│ 景点清单    │ 日程栏      │            地图              │
│  ~230px    │  ~210px    │        剩余全部（最大）        │
│            │            │                             │
│ 想去(S→C)  │ ▸ 第 1 天   │      marker 按天着色         │
│ 待定(S→C)  │   1 中之岛… │      同天按顺序连线           │
│ 未表态      │   2 大阪城… │                             │
│ 不想去      │ ▸ 第 2 天   │                             │
└────────────┴────────────┴─────────────────────────────┘
        └──── 拖拽只在这两栏之间发生，约 260px ────┘
```

**为什么清单在最左、日程在中间**：两栏相邻，从池子拖进某一天是一次短距离横移。
若把地图夹在中间（1440px 下横跨约 1160px），鼠标用户要划过整个地图，触屏基本没法用。
这样排还顺带把地图从 ~840px 放大到 ~940px。

- **模式开关**：`筛选 / 排程`。筛选=两栏（清单+地图），排程=三栏。
- **窄屏降级**：低于约 1000px 时两个侧栏折叠成可切换抽屉，地图始终占主位。
- **当前天**：点某天的标题栏 → 高亮，成为当前天。

### 日程栏按行程长短分两种形态

| 天数 | 形态 |
|---|---|
| ≤ 5 | **平铺**：所有天纵向排列，可直接拖入任意一天；每天可单独折叠 |
| ≥ 6 | **日期胶囊**：顶部一行 `D1 D2 D3 …`，下方只展开当前天 |

阈值取 5 是因为：日程栏高度约 600–700px，一天四五个点占 200–260px，
平铺到第三天就开始滚动，超过五天平铺会退化成无限滚动列表。

**胶囊即当前天选择器**——和"点标题栏设为当前天"是同一个概念，不引入第二套心智模型。
胶囊上带该天的点数角标，一眼看出哪天还空着。

胶囊模式下要往非当前天拖，得先点那个胶囊。可选增强：拖拽悬停在胶囊上 500ms 自动切换
（spring-loaded folders 的做法），但 SortableJS 不原生支持，放到最后看要不要做。

用户可手动在两种形态间切换，阈值只决定默认值。

### 两栏的卡片密度不同

| | 密度 | 内容 |
|---|---|---|
| 景点清单 | 2 行 | 名称 + 时长·价格·关键警示 |
| 日程栏 | **1 行** | 序号 + 名称（截图里就是这个密度） |

日程栏的卡片要短，否则一天四五个点就占满整栏。详情走 hover 高亮和点击 dialog。
- **点选归入**：选定当前天后，点地图图标或右侧卡片即加入；再点已归入的点则移出。
- **拖拽**：右侧 → 容器、容器 ↔ 容器、容器内排序。
- **hover 联动**：hover 卡片（任一侧）→ 地图对应图标放大；hover 图标 → 对应卡片高亮
  （**只高亮不滚动**，列表自动跳动很晕）。
- **点击卡片**：弹详情 dialog（复用 A 阶段那个），不再缩放地图。

### 拖拽方案：内联 SortableJS

HTML5 原生 `dragstart` 系列在移动端 Safari 上根本不触发，直接排除。
剩下"自己写 Pointer Events"和"用库"两条，实测比较后选库：

| 库 | 体积（min / gzip） | 依赖 | 许可 | 最近发布 |
|---|---|---|---|---|
| **SortableJS 1.15.7** | 45.5 KB / 15.1 KB | **零** | MIT | 2026-02-11 |
| dragula 3.7.3 | 14.0 KB / 5.0 KB | contra、crossvent | MIT | 2020-09-29（停更） |
| pragmatic-drag-and-drop | ESM 模块化，需打包器 | — | Apache-2.0 | 活跃 |

SortableJS 提供的，正好是自己写最难的那几块（已逐个在源码里确认）：

| 能力 | 对应我们的问题 |
|---|---|
| `fallbackTolerance` | **点击与拖拽的区分**——卡片既要能点击弹 dialog，又要能拖 |
| `delayOnTouchOnly` | 触屏长按才拖，不和页面滚动打架 |
| `scrollSensitivity` | **容器边缘自动滚动** |
| `pull: 'clone'` | **池子里拖走后原卡留下**——正好是"不移除、只标灰"的语义 |
| `filter` | 排除不可拖的条目 |
| `on{End,Add,Remove,Update}` | 给出 from/to/oldIndex/newIndex，直接更新 `days` |

自己写要处理的是：拖拽阈值、触屏 `touch-action` 与滚动冲突、占位符插入与实时重排、
命中测试、边缘自动滚动、Escape 取消、跨容器 clone 语义。换来的是"零依赖"——
而我们已经在依赖 MapLibre 和 Leaflet，这个卖点本来就不成立。

### 为什么内联而不是 CDN

**失败后果不对等。** MapLibre 挂了有三级降级链（矢量→光栅→Leaflet→静态散点图），
而且地图本来就要联网；**排序不需要网**，因为 unpkg 挂掉就排不了序，是自己给自己
找的故障点——用户可能几个月后才重新打开这个文件。

代价：`trip.html` 从 267 KB 涨到约 312 KB（+17%），仓库多一个第三方文件需手动更新，
要保留 MIT 声明。划算。

放在 `assets/vendor/sortable.min.js`，由 `build.py` 在 `/*__SORTABLE__*/` 处注入——
不直接粘进模板，否则 45 KB 压缩代码会把模板搞得没法读。

### 上下移按钮：无论如何都做

每张卡片带 `↑ ↓` 两个按钮。几行代码，换来三件事：键盘可用、无障碍、
以及万一拖拽在某个环境里出问题时任务仍能完成。

有了它，**拖拽就纯粹是提速手段，不是唯一路径**。

## 校验器新增

| 级别 | 规则 |
|---|---|
| **P0** | `days[].places[].id` 指向不存在的景点 |
| **P0** | 某地点被排到它当天闭馆的日子（`closed_days` × `days[].date` 的星期） |
| **P0** | `days[].n` 重复 |
| P1 | 某天一个地点都没有 |
| P1 | `kind: lodging` 的地点没有出现在任何一天 |
| P2 | 某地点被排入多天却没写 `note`（可能是误操作） |

`days` 缺失时全部跳过——老文件必须继续能用。

每步做完立刻验，用 `mcp__Claude_Browser__` 实际打开页面截图，不只交代码。每步一个 commit。

   避免每轮都手动点一遍。
   *验证*：`validate.py` 零 P0。

3. **marker 编码**：填充/描边/隔离环/序号/双色扇形/酒店图标。
   *验证*：四种状态各截图一张；确认 3px 描边下绿/琥珀/灰可分辨；确认多天点的扇形正确；
   确认与地铁层同开时不糊。

4. **三栏布局与日程栏**：模式开关、平铺/胶囊两种形态、窄屏降级。
   *验证*：1440 / 1100 / 900 三档宽度各截一张，确认地图不被挤变形；

5. **交互**：当前天、点选归入/移出、上下移按钮；引入 SortableJS（vendor + build.py 注入），
   配好 `pull:'clone'`（池子）、`fallbackTolerance`（区分点击）、`scrollSensitivity`（边缘滚动）。
   *验证*：桌面与触屏模拟各跑一遍；确认点击弹 dialog 与拖拽不互相误触发；

6. **顺序线 + hover 联动 + 卡片瘦身 + dialog 复用**。
   *验证*：故意排一条绕路的顺序，确认线上看得出来；hover 双向联动截图。

7. **暂存与回写**：`days` 进 localStorage 自动暂存；`保存` 一并写回 `places.json`。
   *验证*：排一半刷新页面，确认恢复；保存后读回文件确认 `days` 结构正确。

8. **开场问卷补抵达/离开时间**（改 `SKILL.md` 与 `brief.md` 模板）。
   *验证*：模拟一次问答，确认能推出「第 0 天」。

9. **端到端**：拿大阪 28 个点真排一遍两天，记录哪里别扭。

## 已知风险

- **三栏在 1000–1200px 之间会很挤。** 两个侧栏各 ~220px 已经接近中文卡片的下限，
  降级阈值需要实测调，不能拍脑袋定。
- **平铺/胶囊的切换阈值取 5 是估算**，取决于一天平均几个点。实排大阪时确认。
- **SortableJS 与 MapLibre 的 marker 可能抢指针事件**。marker 不参与拖拽，理论上不冲突，
  但两者都在 document 上挂了监听，实测时要专门确认「在卡片上拖拽时地图不平移」。
- **`fallbackTolerance` 的阈值要调**。卡片同时承担点击（弹 dialog）和拖拽两种手势，
  阈值太小会误触发拖拽，太大则拖起来发涩。
- **天色与地铁线色撞车**需实测确认；真撞了就调整天色，不动线路色（那是官方色）。
- **多天点的序号显示**：目前定为显示首个天的序号。实际用起来可能不够，
  届时再看要不要加"hover 某天容器时切到那天的序号"。
